## Intent Analysis

### สิ่งที่ทีมพยายามทำให้เกิดขึ้น

ทีมต้องการ **PM tool ที่สร้างเอง** เพื่อแก้ pain point ที่ tool สำเร็จรูปแก้ไม่ได้ — โดยเฉพาะการระบุว่า**ต้นน้ำของปัญหาอยู่ที่ใคร** (สเปคไม่ครบ / design ไม่ครอบ / code ผิด / test ปล่อยผ่าน) แทนที่จะโยนให้ dev ทั้งหมด

### เป้าหมายของรอบนี้ (MVP)

รอบนี้ไม่ได้พยายามส่งมอบคุณค่านั้นทั้งหมด เป้าหมายคือ **พิสูจน์โครงข้อมูลหลักให้เห็นจริงบนหน้าจอ** — ว่า Requirement, Task, Defect สร้างได้ และเชื่อมโยงกันเป็นสายได้ เมื่อโครงนี้ถูก ค่อยเติมกฎเกณฑ์ (evidence, NFR validation, KPI) ทับลงไปในรอบถัดไปโดยไม่ต้องรื้อ

### ผู้ใช้ที่เกี่ยวข้อง

| ตำแหน่ง | ใช้ระบบทำอะไรในรอบนี้ |
|---------|---------------------|
| **SA** | สร้างและแก้ Requirement |
| **Dev Fullstack** | ดู Task ที่ได้รับ อัปเดตสถานะการทำงาน |
| **Tester** | สร้าง Defect และ link กลับไป Task/Requirement |
| **PM** | ดูภาพรวมและ link งานเข้าหากัน |

## Functional Requirements

### FR1 — Requirement Management

จัดการ Requirement ทั้ง Functional และ Non-Functional แบบ CRUD ครบวงจร

| ID | ข้อกำหนด | เกณฑ์ผ่าน/ไม่ผ่าน |
|----|---------|------------------|
| FR1.1 | ระบบต้องให้ผู้ใช้สร้าง Requirement ใหม่ได้ผ่านฟอร์ม โดยมีข้อมูล: หัวข้อ, รายละเอียด, ประเภท (Functional/Non-Functional), ระดับความสำคัญ MoSCoW, ผู้รับผิดชอบ | สร้างแล้วปรากฏในรายการทันที และข้อมูลครบตามที่กรอก |
| FR1.2 | ระบบต้องบังคับให้ระบุประเภท (Functional / Non-Functional) — ไม่อนุญาตให้บันทึกโดยเว้นว่าง | กดบันทึกโดยไม่เลือกประเภท → ระบบปฏิเสธและแสดงข้อความบอกว่าต้องเลือก |
| FR1.3 | ระบบต้องบังคับให้ระบุระดับความสำคัญเป็นค่าใดค่าหนึ่งใน Must / Should / Could / Won't — ค่าเริ่มต้นคือ Should | บันทึกโดยไม่เลือก → ได้ค่า Should; เลือกค่าอื่น → บันทึกค่าที่เลือก |
| FR1.4 | ระบบต้องแสดงรายการ Requirement ทั้งหมด พร้อมกรองตามประเภทและตามระดับความสำคัญได้ | เลือกกรอง "Functional" → แสดงเฉพาะ Functional; เลือก "Must" → แสดงเฉพาะ Must |
| FR1.5 | ระบบต้องให้แก้ไขทุก field ของ Requirement ที่มีอยู่ได้ และบันทึกค่าใหม่ | แก้แล้วเปิดดูอีกครั้ง → เห็นค่าใหม่ ไม่ใช่ค่าเดิม |
| FR1.6 | ระบบต้องให้ลบ Requirement ได้ โดยถามยืนยันก่อนลบ | กดลบ → มีคำถามยืนยัน; ยืนยัน → หายจากรายการ; ยกเลิก → ยังอยู่ |
| FR1.7 | ระบบต้องแสดงจำนวน Task และ Defect ที่ผูกกับ Requirement นั้นในหน้ารายละเอียด | Requirement ที่มี 2 task 1 defect → แสดง "2 Tasks, 1 Defect" |

### FR2 — Task Management

จัดการ Task ที่แตกมาจาก Requirement

| ID | ข้อกำหนด | เกณฑ์ผ่าน/ไม่ผ่าน |
|----|---------|------------------|
| FR2.1 | ระบบต้องให้สร้าง Task ใหม่ได้ โดยมีข้อมูล: หัวข้อ, รายละเอียด, ผู้รับผิดชอบ, ตำแหน่งของผู้รับผิดชอบ (SA / UX / Dev / Tester), Requirement ต้นทาง | สร้างแล้วปรากฏในรายการ และผูกกับ Requirement ที่เลือกจริง |
| FR2.2 | ระบบต้องบังคับให้ Task ทุกตัวผูกกับ Requirement อย่างน้อย 1 ตัว — ไม่อนุญาต Task ลอย | บันทึกโดยไม่เลือก Requirement → ระบบปฏิเสธพร้อมข้อความอธิบาย |
| FR2.3 | ระบบต้องให้ระบุตำแหน่งของผู้รับผิดชอบเป็นค่าใดค่าหนึ่งใน SA / UX / Dev / Tester | บันทึกโดยไม่เลือกตำแหน่ง → ระบบปฏิเสธ |
| FR2.4 | ระบบต้องแสดงรายการ Task ทั้งหมด พร้อมกรองตามผู้รับผิดชอบ ตามตำแหน่ง และตาม Requirement ต้นทางได้ | เลือกกรองตำแหน่ง "Dev" → แสดงเฉพาะ Task ของ Dev |
| FR2.5 | ระบบต้องให้แก้ไขและลบ Task ได้ โดยการลบต้องถามยืนยันก่อน | เหมือน FR1.5 และ FR1.6 |
| FR2.6 | ระบบต้องแสดงว่า Task นั้นมาจาก Requirement ตัวไหน โดยกดแล้วไปหน้า Requirement นั้นได้ | กดชื่อ Requirement บนหน้า Task → ไปหน้ารายละเอียดของ Requirement ตัวนั้น |
| FR2.7 | ระบบต้องแสดงจำนวน Defect ที่ผูกกับ Task นั้น | Task ที่มี 3 defect → แสดง "3 Defects" |

### FR3 — Defect Tracking

จัดการ Defect พร้อมระบุประเภทเพื่อชี้ต้นน้ำของปัญหา

| ID | ข้อกำหนด | เกณฑ์ผ่าน/ไม่ผ่าน |
|----|---------|------------------|
| FR3.1 | ระบบต้องให้สร้าง Defect ใหม่ได้ โดยมีข้อมูล: หัวข้อ, รายละเอียด, ประเภท, ความรุนแรง, ผู้รายงาน, Task ต้นทาง | สร้างแล้วปรากฏในรายการ และผูกกับ Task ที่เลือก |
| FR3.2 | ระบบต้องบังคับให้ระบุประเภทเป็นค่าใดค่าหนึ่งใน 5 ค่า: Code Bug / SA Gap / Design Gap / Test Escape / NFR Violation | บันทึกโดยไม่เลือกประเภท → ระบบปฏิเสธ; เลือกค่านอก 5 ค่านี้ไม่ได้ |
| FR3.3 | ระบบต้องบังคับให้ระบุความรุนแรงเป็นค่าใดค่าหนึ่งใน Critical / High / Medium / Low | บันทึกโดยไม่เลือก → ระบบปฏิเสธ |
| FR3.4 | ระบบต้องบังคับให้ Defect ทุกตัวผูกกับ Task อย่างน้อย 1 ตัว | บันทึกโดยไม่เลือก Task → ระบบปฏิเสธพร้อมข้อความอธิบาย |
| FR3.5 | ระบบต้องแสดงรายการ Defect ทั้งหมด พร้อมกรองตามประเภทและตามความรุนแรงได้ | เลือกกรอง "SA Gap" → แสดงเฉพาะ SA Gap |
| FR3.6 | ระบบต้องให้แก้ไขและลบ Defect ได้ โดยการลบต้องถามยืนยันก่อน | เหมือน FR1.5 และ FR1.6 |
| FR3.7 | ระบบต้องแสดงจำนวน Defect แยกตามประเภททั้ง 5 ประเภทในหน้ารายการ | มี 2 Code Bug 1 SA Gap → แสดงตัวเลข 2 และ 1 ตรงประเภทนั้น |

### FR4 — Traceability (สายเชื่อมโยง)

หัวใจของรอบนี้ — ทำให้เห็นสาย Requirement → Task → Defect ทั้งสองทิศทาง

| ID | ข้อกำหนด | เกณฑ์ผ่าน/ไม่ผ่าน |
|----|---------|------------------|
| FR4.1 | ระบบต้องแสดงสายเชื่อมโยงจาก Requirement ลงไปถึง Task และ Defect ทั้งหมดที่อยู่ใต้มัน (forward trace) | เปิด Requirement ที่มี 2 Task และแต่ละ Task มี 1 Defect → เห็นทั้ง 2 Task และทั้ง 2 Defect ในหน้าเดียว |
| FR4.2 | ระบบต้องแสดงเส้นทางย้อนกลับจาก Defect ขึ้นไปถึง Task และ Requirement ต้นทาง (backward trace) | เปิด Defect → เห็นชื่อ Task และชื่อ Requirement ต้นทาง และกดไปหน้านั้นได้ |
| FR4.3 | ระบบต้องระบุ Requirement ที่ยังไม่มี Task ผูกอยู่เลย ให้เห็นชัดในรายการ | Requirement ที่ไม่มี Task → มีเครื่องหมายหรือข้อความบอกว่า "ยังไม่มี Task" |
| FR4.4 | เมื่อลบ Requirement ที่ยังมี Task ผูกอยู่ ระบบต้องเตือนและบอกจำนวน Task ที่จะกำพร้า พร้อมให้เลือกว่ายกเลิกหรือลบ Task ตามไปด้วย | ลบ Requirement ที่มี 2 Task → ข้อความเตือนระบุ "2 Tasks"; เลือกลบตาม → Task หายทั้งคู่; เลือกยกเลิก → ไม่มีอะไรถูกลบ |
| FR4.5 | เมื่อลบ Task ที่ยังมี Defect ผูกอยู่ ระบบต้องเตือนแบบเดียวกับ FR4.4 | เหมือน FR4.4 แต่ระดับ Task → Defect |

### FR5 — การเลือกผู้ใช้ (แทน Authentication)

| ID | ข้อกำหนด | เกณฑ์ผ่าน/ไม่ผ่าน |
|----|---------|------------------|
| FR5.1 | ระบบต้องมี dropdown ให้เลือกว่ากำลังใช้งานในฐานะใคร จากรายชื่อผู้ใช้ที่กำหนดไว้ล่วงหน้า พร้อมตำแหน่งของแต่ละคน | เลือกชื่อ → ชื่อนั้นปรากฏเป็นผู้ใช้ปัจจุบันบนหน้าจอ |
| FR5.2 | ระบบต้องใช้ผู้ใช้ที่เลือกไว้เป็นค่าเริ่มต้นของ field ผู้รายงาน/ผู้รับผิดชอบ เมื่อสร้างรายการใหม่ | เลือกเป็น "สมชาย" แล้วสร้าง Defect → ผู้รายงานตั้งต้นเป็น "สมชาย" |
| FR5.3 | ระบบต้องจำผู้ใช้ที่เลือกไว้ข้าม session (ปิดแล้วเปิดใหม่ยังเป็นคนเดิม) | เลือกผู้ใช้ → refresh หน้า → ยังเป็นคนเดิม |

### FR6 — การเก็บข้อมูล

| ID | ข้อกำหนด | เกณฑ์ผ่าน/ไม่ผ่าน |
|----|---------|------------------|
| FR6.1 | ข้อมูลทั้งหมดต้องคงอยู่ใน `localStorage` และยังอยู่หลัง refresh หรือปิดเปิด browser ใหม่ | สร้าง 3 รายการ → ปิด browser → เปิดใหม่ → ยังเห็นทั้ง 3 รายการ |
| FR6.2 | ระบบต้องรองรับการ export ข้อมูลทั้งหมดเป็นไฟล์ JSON และ import กลับเข้ามาได้ | export ได้ไฟล์; ลบข้อมูลทั้งหมด; import ไฟล์นั้น → ข้อมูลกลับมาครบเท่าเดิม |
| FR6.3 | เมื่อข้อมูลใน `localStorage` เสียหายหรืออ่านไม่ได้ ระบบต้องไม่ค้างหรือจอขาว แต่แสดงข้อความบอกผู้ใช้และให้เริ่มใหม่ได้ | ใส่ข้อมูลผิดรูปแบบใน localStorage → เปิดแอป → เห็นข้อความอธิบาย ไม่ใช่จอขาว |
| FR6.4 | เมื่อ `localStorage` เต็ม ระบบต้องแจ้งผู้ใช้และแนะนำให้ export ข้อมูลออกไปก่อน ไม่ใช่ล้มเหลวเงียบๆ | เขียนจนเต็มโควตา → เห็นข้อความแจ้งเตือน และข้อมูลเดิมไม่หาย |

## Non-Functional Requirements

ทุกข้อมีตัวเลขวัดได้ตามกฎ Requirements Quality ของ Inception phase

| ID | ข้อกำหนด | ตัวเลขเป้าหมาย | วิธีวัด |
|----|---------|---------------|--------|
| NFR1 | ความเร็วในการโหลดหน้าแรก | First Contentful Paint ≤ 1.5 วินาที บนเครื่อง desktop ทั่วไป ที่ข้อมูล 100 รายการ | Chrome DevTools Lighthouse |
| NFR2 | ความเร็วในการตอบสนองต่อการกด | การกรอง/ค้นหา/เปลี่ยนหน้า ต้องแสดงผลภายใน 200 มิลลิวินาที ที่ข้อมูล 500 รายการรวมทุก entity | วัดด้วย Performance API ในเบราว์เซอร์ |
| NFR3 | ปริมาณข้อมูลที่รองรับ | รองรับรวมกัน 500 รายการ (Requirement + Task + Defect) โดย NFR2 ยังผ่าน | สร้างข้อมูลทดสอบ 500 รายการแล้ววัด |
| NFR4 | ความเข้ากันได้ของเบราว์เซอร์ | ทำงานถูกต้องบน Chrome, Firefox, Safari รุ่นล่าสุด และรุ่นก่อนหน้า 1 เวอร์ชัน | ทดสอบด้วยมือทั้ง 6 ชุดเบราว์เซอร์/เวอร์ชัน |
| NFR5 | การเข้าถึงสำหรับผู้ใช้ที่หลากหลาย (Accessibility) | ผ่าน WCAG 2.1 ระดับ AA ในส่วน: contrast ratio ≥ 4.5:1 สำหรับตัวอักษรปกติ, ทุก interactive element เข้าถึงด้วย keyboard ได้, ทุก form field มี label ที่ screen reader อ่านได้ | Lighthouse Accessibility score ≥ 90 และทดสอบ keyboard navigation ด้วยมือ |
| NFR6 | ความครอบคลุมของ test | มี unit test อย่างน้อย 1 ตัวต่อ 1 requirement ที่ระบุไว้ในเอกสารนี้ (Minimal test strategy) และทุก component มี happy-path test อย่างน้อย 1 ตัว | นับจำนวน test เทียบกับจำนวน FR; รัน suite ต้องผ่านทั้งหมด |
| NFR7 | ขนาดไฟล์ที่ส่งถึงผู้ใช้ | production bundle (gzip) ≤ 300 KB | `vite build` แล้วดูขนาด output |

## ความเสี่ยงที่ทีมรับรู้และยอมรับแล้ว

บันทึกไว้เพราะเป็นหนี้ที่ต้องจ่ายคืน ไม่ใช่สิ่งที่หายไปเอง

| ID | ความเสี่ยง | ผลกระทบ | ต้องจ่ายคืนเมื่อไหร่ |
|----|-----------|--------|---------------------|
| R1 | **ไม่มี authentication** — ใครเปิดแอปก็แก้หรือลบข้อมูลของใครได้ทั้งหมด และ "ผู้ใช้ปัจจุบัน" เป็นเพียงการเลือกจาก dropdown ไม่ใช่การยืนยันตัวตน | ข้อมูลผู้รับผิดชอบและผู้รายงานไม่มีความน่าเชื่อถือ ดังนั้น**ห้ามนำข้อมูลจากรอบนี้ไปใช้คำนวณ KPI รายคน** เพราะใครก็แก้ชื่อคนอื่นได้ | ก่อนนำระบบไปใช้กับทีมจริง และก่อนเปิดฟีเจอร์ KPI |
| R2 | **ข้อมูลอยู่ใน localStorage** — ผูกกับเครื่องและเบราว์เซอร์ของแต่ละคน ทีมแชร์ข้อมูลกันไม่ได้ ล้าง browser data แล้วข้อมูลหายถาวร | ระบบนี้ยังใช้ทำงานเป็นทีมจริงไม่ได้ ใช้ได้แค่สาธิตและตรวจ flow; และต้องเขียน data layer ใหม่ตอนขึ้น backend | รอบถัดไป — บรรเทาชั่วคราวด้วย FR6.2 (export/import) |
| R3 | **ตัด NFR validation และ evidence enforcement ออก** | รอบนี้จึงยังไม่ได้ส่งมอบคุณค่าที่ทำให้ระบบนี้ต่างจาก Trello หรือ Notion — ซึ่งคือเหตุผลที่ทีมตัดสินใจสร้างเองตั้งแต่แรก | รอบถัดไป ควรเป็นลำดับความสำคัญสูงสุด |
| R4 | **12 คนทำงานขนานบน 3 modules ที่แชร์โครงข้อมูลเดียวกัน** (Requirement ↔ Task ↔ Defect ผูกกันหมด) | เสี่ยง merge conflict สูงที่ไฟล์ type และ storage layer | ต้องตัดสินใจก่อนเริ่มเขียนโค้ด — ดู OQ2 |
